SnapIPC Android SDK

SnapHalo connects an Android app to an IPCMobile SnapHalo barcode scanner over Bluetooth Low Energy (BLE). The SDK parses the scanner's NFC identity, discovers the device, exchanges Nordic UART commands, and delivers barcodes, trigger events, firmware versions, and battery telemetry. The Android SDK handles NFC intents, foreground NFC reads, runtime permission prompts, and the Bluetooth-enable dialog through SnapHaloAndroid, using the host Activity for system UI.

Start new integrations with com.ipcmobile.snapipcsdk.SnapHalo. Its barcode, light, and battery properties group related operations; events publishes typed notifications. Protocol handling and scanner listeners are internal implementation details. The package links below provide the full API reference.

API visibility

Create SnapHalo() and attach SnapHaloAndroid(activity, snapHalo, onError) for Android pairing. Identities, their parser and credentials, raw responses, the session, and logging are internal implementation details. Public events and query results use standalone barcode and device models.

Android applications use the adapter for NFC, permission prompts, and Bluetooth readiness. It preserves secure NFC credentials; LE OOB parsing and pairing data remain internal to the SDK. connect is internal. startPairing on the shared client is the iOS entry point; Android apps attach SnapHaloAndroid.

SnapHalo exposes IBarcodeReader, ILight, and IBattery through the grouped properties. IBarcodeReader exposes ISymbology, IDiagnostics, IImaging, IImages, and IOcr through its symbology, diagnostics, imaging, images, and ocr properties. Call grouped operations through these properties; the flat SnapHalo methods are no longer available. Internal control classes implement these interfaces against one shared scanner session and disposal guard. SnapHalo owns that session, event delivery, and cleanup; general device methods delegate to the device control. Ordinary query methods use a fixed three-second timeout; image transfer accepts a separate timeoutMs, defaulting to 120 seconds. Use the exact identifiers getSymobologies and LightbarColor in application code.

Create one SnapHalo() per scanner owner. The SDK accepts response frames with either a valid calculated four-byte checksum or the exact legacy AA BB CC DD trailer. Other trailers are rejected. The legacy marker does not detect altered payloads.

For continuous scanning, call setContinuousScanInterval after setScanMode. Selecting a continuous mode sets the interval to 100 ms. Read details().scanIntervalMs, details().beepEnabled, and details().vibrateEnabled to inspect the scanner's reported settings. details().channelSoundingEnabled reports the channel sounding setting. barcode.symbology uses the HSM decoder's session settings (sub-command 0x0E). read returns the flags word and optional accepted lengths. setFlags replaces the entire word, including the enable bit; use update to change selected bits without losing the others. update reads first and confirms the result by default. setLengthRange applies only to formats with a length range. These decoder settings can revert when the scan engine is re-enabled and are separate from barcode.setSymbology and details().barcodeEnable. resetToDefaults changes decoder settings only; the scanner can reapply its saved enabled-format list when the engine restarts. It accepts SYM_POSTALS or SYM_ALL for a group reset. setRedundancy also accepts SYM_ALL; redundancy reads one format. StarScanner marks HSM redundancy command 0x21 for firmware verification, so confirm its behavior on a scanner before relying on it.

barcode.diagnostics reads require an active scan engine. A failed read may indicate an inactive engine, older firmware, or a connection that has not completed NFC setup; the scanner does not distinguish these causes. isHsmAvailable() probes with engineType() and returns false on an ordinary query failure. Imager serial and part numbers are split only when a separate serial-number read matches the start of the combined scanner response.

barcode.imaging uses HSM settings for the current scan-engine session. The scanner may reset writes when the engine is reinitialized. lightsMode(current = false) reads the decoder default rather than the active mode; the setter has the same selector. setSleepTimeoutMs rejects negative values. This engine timeout is separate from the scanner's idle and power-off timeouts. StarScanner marks the HSM sleep-timeout command for firmware verification. Decode-options readback uses the firmware's little-endian layout, while writes use big-endian fields. light.setDecodeAimer and light.setDecodeLight control individual outputs, not the combined scan-time mode.

barcode.imaging.centeringWindowEnabled uses HSM sub-command 0x10, and the extended centeringMode uses 0x11. The existing Boolean barcode.setCenteringMode(enabled) uses legacy sub-command 0x04 and has no readback. Window modes use whatever rectangle the engine already has; this API does not set its corners. centeringWindowLimits reports allowed coordinates for the standard or extended window. showDecodeWindow controls a debug overlay. setScanningMode is set-only, and StarScanner marks its 0x18 behavior unconfirmed against firmware.

setExposureSettings validates all values before sending, writes at most eight parameter/value pairs per HSM request, and stops if any request fails. The decoder reads all eight slots even for smaller updates, so the SDK repeats the last real pair in unused slots. exposureSettingsRaw() returns eight raw pairs; StarScanner notes that the decoder may not return meaningful parameter IDs. Treat its output as diagnostic until checked on a scanner.

barcode.images uses a 120-second timeout by default for image transfers; lastImageInfo() remains a short settings query. lastImage() returns the engine's stored image, often raw 8-bit gray, with exposure and gain. Check ScannerImage.format before decoding its bytes; RAW_GRAY needs its width and height to display. The SDK accepts image reply payloads up to 2 MiB for HSM 0x15. Progress callbacks can skip intermediate fractions on a fast transfer and receive 1f on success. Image retrieval is unverified on hardware.

barcode.ocr.settings() reads the active HSM OCR mode and template bitmask. userTemplate() reads the custom template text and its mode. A new custom template must be 1..320 ASCII characters and follow the decoder's OCR grammar. Writing it does not activate the user-template bit; call the existing barcode.setOcrModeTemplate(mode, OcrTemplate.User.mask) when the engine should use it. OCR HSM readback and custom-template behavior remain unverified on hardware.

clearBleBonding() restarts scanner advertising, and powerOff() ends the BLE connection. Both complete when the command is written; observe connection events for the resulting state. SnapHalo activates the decoder when a connection starts.

readRssi() requires a connected BLE link, returns a dBm reading, and emits that reading to rssi. Collect the flow before requesting readings. It has no replay and retains only the newest pending reading for a slow collector. The SDK does not poll RSSI automatically. Failed reads throw and do not emit.

Collect SnapHaloEvent.OnBarcodeScanned for decoded barcodes. Other events cover connection state (including the captured error), trigger changes, battery, and firmware. The stream has no replay and buffers 64 notifications; slow subscribers lose oldest events. Keep collectors short and start collection before scanning. Each decoded barcode produces one public scan event. Raw response callbacks remain internal. Cancel collectors with the owning scope; disposing the client does not complete a SharedFlow.

Commands complete on BLE write and throw on failure; they do not return AiWedge-style acknowledgement Booleans. Queries await device replies. The default transport reports connection failures through connection events. Idle timeout is in minutes and power-off timeout in seconds. Scan modes use BarcodeScanMode in models, alongside device details, battery readings, light-bar colors and symbology settings. Every production declaration in protocol is internal or private.

For explicit disconnect, cancel the adapter's pending connection and call snapHalo.disconnect(). On final owner destruction close the Android adapter, then call snapHalo.dispose() or snapHalo.close(). Disposal is idempotent; create a new client for a new owner. There is no separate initialize(context): the Android adapter needs an Activity for system dialogs. iOS consumers use startPairing(onError) to present the NFC sheet and pair from a scanned tag.

Requirements and installation

The library declares Android API 26 as its minimum and builds against API 37 with a JDK 17 toolchain. Build this repository with its Gradle wrapper (the daemon criteria request JDK 25) and an installed Android SDK. Set sdk.dir in the root local.properties, or configure the SDK through Android Studio. A physical Android device with BLE and a SnapHalo scanner are needed for hardware validation. NFC hardware is needed when the app uses tap-to-connect.

The examples below assume an AndroidX ComponentActivity with the Activity Result API and lifecycleScope available through the host application's AndroidX dependencies. The SDK itself has no Compose UI requirement.

Activity integration: NFC and permission prompts

Create one SnapHaloAndroid in your ComponentActivity.onCreate, after super.onCreate and before the Activity starts. This Android-only SDK adapter:

  • Requests missing BLE runtime permissions automatically on first start.

  • Processes the Activity's launch intent and subsequent onNewIntent deliveries.

  • Enables NFC reader mode while resumed and disables it when paused.

  • Extracts Bluetooth LE OOB carrier data or a legacy SnapHalo URI from NFC intents and records.

  • Holds the latest scanned identity until all permissions are granted.

  • Opens Android's Bluetooth-enable prompt when needed before connection.

  • Cancels its work and unregisters its Activity hooks when the Activity is destroyed.

This complete Activity example collects events before the adapter can connect. It owns the client for the Activity's lifetime, including while paused, and releases it on destruction. Add the manifest routing shown below to enable cold launch from a tag.

import android.os.Bundle
import android.widget.TextView
import android.widget.Toast
import androidx.activity.ComponentActivity
import androidx.lifecycle.lifecycleScope
import com.ipcmobile.snapipcsdk.SnapHalo
import com.ipcmobile.snapipcsdk.android.SnapHaloAndroid
import com.ipcmobile.snapipcsdk.events.SnapHaloEvent
import kotlinx.coroutines.CoroutineStart
import kotlinx.coroutines.Job
import kotlinx.coroutines.launch

class MainActivity : ComponentActivity() {
    private val snapHalo = SnapHalo()
    private lateinit var androidSdk: SnapHaloAndroid
    private var eventJob: Job? = null

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        val status = TextView(this).apply { text = "Tap a SnapHalo scanner" }
        setContentView(status)

        eventJob = lifecycleScope.launch(start = CoroutineStart.UNDISPATCHED) {
            snapHalo.events.collect { event ->
                when (event) {
                    is SnapHaloEvent.OnBarcodeScanned ->
                        status.text = "${event.barcode.value} (${event.barcode.symbology})"
                    is SnapHaloEvent.OnConnectionStatus ->
                        status.text = event.errorMessage ?: event.connectionState.toString()
                    else -> Unit
                }
            }
        }
        androidSdk = SnapHaloAndroid(this, snapHalo) { message ->
            Toast.makeText(this, message, Toast.LENGTH_LONG).show()
        }
    }

    override fun onDestroy() {
        androidSdk.close()
        eventJob?.cancel()
        snapHalo.dispose()
        super.onDestroy()
    }
}

The adapter disconnects the previous scanner session and connects internally after a valid tap and successful permission/Bluetooth checks. You do not need to implement onNewIntent, onRequestPermissionsResult, onActivityResult, or NfcAdapter.ReaderCallback. If you override Activity result or intent callbacks for other app features, call super so AndroidX can deliver the SDK callbacks.

The identity callback constructor and NFC parsing helpers are internal. A public four-argument constructor also accepts dispatchConnection: (suspend () -> Unit) -> Unit for a short-lived NFC dispatch Activity. It handles dispatched intents without foreground reader mode; the host must run the supplied work in a scope that outlives that Activity. All adapter methods run on the main thread. Pass the same SnapHalo instance to the adapter and to application code that collects events and issues commands. The shared demo uses this public constructor.

Create only one adapter per Activity. Do not create the adapter in Compose recomposition. It is Activity-bound and must be recreated with the Activity, even when the client is owned by a longer-lived ViewModel or service. Permission/enable-dialog state survives saved-state recreation. Secure pending tap credentials survive rotation in memory; process death requires a fresh tap. An in-progress BLE connection is cancelled on destruction and is not restored automatically; tap again after recreation.

Bluetooth permissions

The AAR declares NFC and BLE permissions; the adapter requests only missing runtime grants. NFC is a normal manifest permission and has no runtime dialog. The permission set for an app targeting current Android versions is:

Android versionRuntime permissions requested by the SDK
Android 12 / API 31 and newerBLUETOOTH_SCAN, BLUETOOTH_CONNECT
Android 8–11 / API 26–30ACCESS_FINE_LOCATION

The adapter never connects after a denied or partial grant. It reports the issue through onError; another valid tap or androidSdk.requestPermissions() can request the missing grants again. Android may suppress prompts after repeated refusal; the user must then grant permission in app settings and tap again. A normal pause/resume does not repeatedly open denied permission dialogs. androidSdk.missingPermissions() reports the current missing grants.

When Bluetooth is off, the adapter requests enablement before delivering the identity. Cancelling that dialog reports an error and discards the pending tap. The SDK does not turn Bluetooth on silently. Older Android releases may also require system Location to be enabled for BLE discovery. Foreground use is covered here; background scanning has additional Android requirements.

The SDK declares BLUETOOTH_SCAN with neverForLocation and caps legacy Bluetooth and location permissions at API 30. See Android's Bluetooth permission guidance. Route NFC tags and ipcstar://nfc links through SnapHaloAndroid.handleIntent() or its foreground reader mode so the adapter can manage permissions and Bluetooth.

NFC manifest routing

Foreground reader mode works without an intent filter while the Activity is resumed. To open the app from a SnapHalo NFC tag or ipcstar://nfc link, the host must declare the destination Activity, because the SDK cannot choose an app's UI. The SDK manifest already contributes android.permission.NFC and an optional NFC feature declaration.

Add a VIEW filter to the app's Activity and a separate NFC alias after that Activity declaration:

<activity
    android:name=".MainActivity"

    <intent-filter>
        <action android:name="android.intent.action.VIEW" />
        <category android:name="android.intent.category.DEFAULT" />
        <category android:name="android.intent.category.BROWSABLE" />
        <data android:scheme="ipcstar" android:host="nfc" />

</activity>
<activity-alias

The SDK supplies snapipc_nfc_dispatch_permission: empty on older Android and android.permission.DISPATCH_NFC_MESSAGE on API 37+. This protects the NFC entry when targeting Android 17 while keeping ordinary launcher and VIEW access on the main Activity. See Android's NFC manifest requirements. NFC must be enabled by the user in system settings; phones without NFC can still use a valid VIEW intent. The adapter tolerates absent or disabled NFC hardware.

For custom routing, androidSdk.handleIntent(intent) returns whether a valid identity was accepted; do not also forward intents that AndroidX already delivers to the adapter. SnapHaloNfc and its identity-returning helpers are internal.

Accepted tag/link example: ipcstar://nfc?id=AABBCCDDEEFF. The internal parser returns null for invalid input, normalizes address separators and case, and accepts percent-escaped IDs. Unrelated intents and invalid tag records are ignored.

Connection lifecycle

Import com.ipcmobile.snapipcsdk.models.ConnectionState. This replaces the former SnapHaloConnectionState name without changing the enum values. Both snapHalo.getConnectionState() and SnapHaloEvent.OnConnectionStatus.connectionState use ConnectionState. Update old imports; there is no alias for the previous name.

A typical connection progresses through RequestingBluetooth, Scanning, Connecting, DiscoveringServices, and Connected. The Activity adapter's permission prompts happen before these transport states. Scanning and initial connection each have a 20-second timeout. Android discovery matches the address, an IPCSTAR name suffix, service data, or manufacturer data.

With the default Kable transport, connection failures produce an Error connection event with a captured errorMessage; they normally do not escape connect as exceptions. Collect SnapHaloEvent.OnConnectionStatus and use Connected as the readiness signal. The adapter's onError reports permission/NFC/readiness errors and thrown connection errors; transport-reported errors arrive in connection events, with the error captured in event.errorMessage. Returning from connect is not a command acknowledgement.

Unexpected loss of an established link triggers reconnection, with a one-second delay after failed attempts. Explicit disconnect stops reconnection and returns to WaitingForNfc. On connection the SDK activates decoding, requests firmware, and starts battery polling immediately and then every minute.

NFC tap authentication

Modern LE OOB records carry a BLE address, address type, and optional Cr/Nr credentials. A complete credential triggers the scanner's raw F0 challenge/ response handshake; Connected is emitted only after success. The transport negotiates a larger Android MTU and checks that the 34-byte authentication response fits. Rejection, timeout or an insufficient MTU produces Error and a message.

The SDK keeps application-layer proof status internally, independently of OS Bluetooth bonding. A malformed modern record does not fall back to a URI on the same tag. A valid address-only record or legacy URI has no tap proof. New firmware may restrict commands on those connections. A fresh tap replaces an active attempt. Credentials survive a pending permission prompt across rotation in memory; process death requires a new tap. No credential bytes are saved or logged.

Cold launch still depends on the NFC tag's dispatch records. An Android Application Record naming the old StarScanner app must be updated in firmware/tag configuration to launch the SnapHalo demo automatically. Foreground reader mode does not depend on that package routing. This migration does not rewrite NFC tags.

Authorization status

Authorization support is internal to the SDK. App code cannot configure customer signers, hardware-trust policy, factory enrollment, or administrator keys. These implementation types and their SnapHalo accessors are excluded from the public Kotlin and Swift API and from this reference.

Observe snapHalo.authLevel and OnConnectionStatus.authLevel for scanner status: Locked means no NFC proof completed, Tapped means a required customer proof is pending, and Operational means authentication succeeded. Missing credentials or rejected proof produce a connection Error with a descriptive errorMessage. Scanners requiring customer keys need internal SDK credential configuration; the public SDK has no host-supplied signer hook.

Verified identity remains observable through snapHalo.hardwareSerial and OnConnectionStatus.hardwareSerial. Optional attestation unavailability can emit OnSecurityWarning. These read-only diagnostics do not expose trust or administrator configuration.

Manual migration validation

Record phone model/OS, Nordic firmware and scan-engine firmware with each result. The Android demo now exposes Unique scan mode. Device controls and typed queries are SDK APIs; test them from the integrating application's command UI or a small host screen using the calls above.

  • Tap a legacy URI tag, grant permissions, and verify barcode, trigger, firmware and battery events. Repeat with Bluetooth disabled and after denying permissions.

  • Tap a modern OOB tag while the app is foregrounded. Confirm Connected follows authentication; then repeat a cold launch to check the tag's MIME/AAR routing for the installed app package.

  • Test a stale/rejected credential, link loss during authentication, a new tap during connection, and explicit disconnect during discovery. None should leave a ready connection after failure/cancellation. Fresh taps must recover.

  • Select Single, Continuous and Unique modes; scan repeated barcodes, reconnect, and relaunch the app. Query snapHalo.details() and record which settings the scanner retains.

  • Query device model, both firmware versions, battery and all parameters. Compare values with StarScanner on the same hardware. Change a setting, query again, and verify the scanner reports the new value.

  • Exercise the nine migrated command variants with supported firmware. Verify light-bar colors, melodies/beeps, timer units, centering, aimer/light and OCR templates. Restore the user's settings after the test. Unsupported firmware may ignore a command even when its BLE write succeeds.

  • Interrupt a fragmented barcode/parameter reply by moving out of range, then reconnect. Confirm later replies decode without old data. Verify DotCode labels.

  • Rotate during the permission prompt; then repeat after OS process recreation. A credential should remain in memory for rotation, and require a fresh tap after process death. Check that diagnostics contain no Cr/Nr or authentication packets.

  • On macOS/Xcode, build :snapipc-sdk:assembleSnapIPCSDKReleaseXCFramework, run :snapipc-sdk:iosSimulatorArm64Test (or the host's simulator architecture), and repeat connection, query, reconnect and NFC-host integration on a physical iPhone.

Firmware upload is included in the current Android AAR; validate upload, reboot, confirmation, and active-image readback on hardware before shipping an updater. Android ranging and a discovery/pairing UI remain separate additions.

Ownership and cleanup

Create one client per owner (Activity, ViewModel, or service), not per Compose recomposition. The client owns one scanner and its BLE resources. The SnapHaloAndroid adapter is Activity-bound and does not own or dispose the client.

For an explicit disconnect, call androidSdk.cancelPendingConnection() on the main thread to discard queued NFC work, then await snapHalo.disconnect() in the owner's coroutine scope. The same client can later connect again.

For final destruction, the Activity example closes the adapter, cancels its event job, disposes the client, and calls super.onDestroy(). dispose() / close() release BLE resources and cancel polling and reconnection. Disposal is idempotent; a disposed client must be replaced before use.

For a ViewModel-owned client, recreate the Android adapter for each Activity, close the adapter when that Activity is destroyed, and dispose the client in the ViewModel's onCleared(). Do not dispose a retained client on Activity rotation. Cancel event collectors when their respective owners end. Service integrations must still provide an Activity for the adapter's system UI.
